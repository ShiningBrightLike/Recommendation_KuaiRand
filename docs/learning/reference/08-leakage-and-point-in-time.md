# 08 泄漏与 point-in-time 审计

## 什么是 point-in-time 风险

如果模型在预测某一时刻的曝光时，使用了只能在未来才知道的统计量，离线指标就会被抬高。典型例子是视频统计特征按全期聚合，而不是按预测时刻之前的窗口聚合。

时间切分可以隔离日志行，但不会自动修复特征生成过程。必须同时回答：

1. 这列特征的观测时间是什么？
2. 它的聚合窗口是否早于当前曝光？
3. train、val、test 是否使用了相同的生成规则？

## 当前仓库的审计结论

首轮审计比较了“保留全部视频统计特征”和“删除全部 51 列统计特征”两种变体。它发现指标差异明显，说明统计特征有预测作用，同时也说明未来信息风险值得认真处理。

这份审计是风险信号，不是严格修复：

- 删除全部统计特征是上界式对照，不等于逐列 point-in-time 重算；
- 单特征 AUC 是关联证据，不是泄漏证明；
- 报告中的 test 数字属于历史审计，不得拿来做当前模型选择；
- 严格修复需要按训练窗口重新生成统计列，并重新训练对照。

## 评估侧表与泄漏不是一回事

sidecar 中的 user_id、video_id、row_id 和原始日期用于分组、稳定排序和审计；它们不进入模型输入。sidecar 的存在不会使统计特征自动变得安全，二者要分开检查。

## 严格重算的验收清单

未来实现 point-in-time 版本时，至少要记录：

- 每列统计特征的聚合窗口和截止时间；
- train/val/test 各自的可用历史范围；
- 生成脚本和输入数据版本；
- 全量特征与严格窗口特征的同 seed 对照；
- 四个任务和门控任务的 AUC 变化；
- 用户级曝光内排序指标是否同步变化；
- 是否仍然只用 val 做候选决策。

在这些证据完成前，教程统一使用“存在 point-in-time 风险”的表述，不写成“泄漏已经解决”。
